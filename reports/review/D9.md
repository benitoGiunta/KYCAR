## 5. Points ouverts / tensions instruits (sans décision)

- **O13 — `ingestFlags` sur 16 bits, 14 vs 17 drapeaux.** Faits : `src/types/vocabularies.ts` retient
  les **17** codes d'`EX-DATA-45` en signalant la divergence de la source ; D9 n'en utilise que
  **3** (`ENUM_UNKNOWN`, `MODEL_UNRESOLVED`, `PRICE_MISSING_UNDECLARED`) et stocke les drapeaux en
  `readonly string[]`, jamais en champ de bits — la contrainte des 16 bits n'est donc ni exercée ni
  contredite par ce lot. Les constats `R-D9-02/03/05/06/07/14` portent chacun sur un drapeau du
  vocabulaire non posé ; les corriger porterait D9 de 3 à ~11 drapeaux utilisés, ce qui rapproche du
  seuil de 16 sans le franchir.
- **O14 — table NUTS-2 BE `[EXTRAPOLÉ]` (`EX-DATA-53`).** Faits : `BE_POSTAL_RANGES` et
  `REGION_VALUES` existent en dur dans `src/types/vocabularies.ts` ; **D9 ne les utilise pas**. La
  surface autorisée de 2dehands ne sert **aucun code postal** (`probe-LOT-N` : `location` =
  `cityName`/`countryAbbreviation`/`lat`/`long`), donc la troncature de code postal exigée par O14
  est **sans objet ici** : il n'y a pas de code postal à tronquer, et la sonde confirme qu'aucun ne
  survit. La conséquence est que `regionCode` est structurellement INCONNU sur cette source — fait,
  pas décision. Le filtre Région se dégraderait entièrement si ce provider devenait le défaut.
- **O15 — `Model.bodyTypes` vide.** Fait : la taxonomie chargée par le lot expose bien
  `bodyTypes: []` (constaté sur les 53 modèles Opel) ; D9 mappe une carrosserie par annonce
  (`mapBodyType`) mais ne l'expose dans aucun agrégat — la donnée normalisée est actuellement
  **inutilisée en aval**, comme tous les champs d'énumération de `NormalizedListing`.
- **O17 — budget 200 ms / `EX-NFR-5`, et `EX-NFR-9`.** Fait nouveau apporté par cette revue : sur une
  source `AGGREGATE_SURFACE`, le coût dominant n'est pas le calcul mais le **nombre d'allers
  réseau** — 296 requêtes séquentielles à l'ouverture du snapshot avec l'univers de marques par
  défaut, 53 de plus par carte-marque développée (`R-D9-16`). Le garde-fou §9.3 n° 1 (précalcul mis
  en cache) est la contre-mesure prévue par l'architecture ; elle n'est pas implémentée.
- **Tension §9.3 vs §6.3.** `ARCHITECTURE.md` §6.3 décrit `AGGREGATE_SURFACE` comme faisant « un
  aller réseau par appel », ce que le code respecte à la lettre ; §9.3 pose comme « contrainte non
  négociable » que la baseline soit précalculée/mise en cache. Les deux textes ne sont pas
  réconciliés pour un provider `AGGREGATE_SURFACE` : c'est le point que `R-D9-16` matérialise.
- **Tension « fourchettes mode 1 » vs biais d'échantillon.** `coverageNote` reconnaît honnêtement que
  les fourchettes sont calculées sur 30 annonces par page, dont l'audit 1.5 dit que ~95 % sont
  promues (DAGTOPPER). Les fourchettes prix/km/année de l'écran A seraient donc systématiquement
  biaisées vers les annonces payantes, alors que seul le **compte** est exhaustif. Le lot le
  documente ; aucune exigence ne tranche si une fourchette biaisée peut être affichée sans un
  marqueur visuel équivalent à `sample_biased = true`. Fait porté à l'arbitrage, non tranché ici.
- **AC-01 (validation juridique 2dehands) non levée.** Le rapport du chantier 1 en fait le
  **prérequis du branchement réel du mode 1**. Le code est prêt et licite dans sa surface, mais
  aucun élément du dépôt n'atteste la décision juridique ; `R-D9-19` relève l'absence de cette
  mention dans `/mentions`.
